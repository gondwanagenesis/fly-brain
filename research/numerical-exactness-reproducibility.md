# Exact integration and reproducible parallel reduction for the whole-brain LIF kernel

## Bottom line

The exact-integration half of this field is **already fully absorbed** into this codebase: Rotter–Diesmann's propagator (§5.1 of ROADMAP.md) and the Morrison/Hanuschkin off-grid correction are exactly the accepted literature fix for what dt = 0.1 ms costs (§4 of HANDOFF.md independently rediscovers Hansel et al. 1998's synchronization-error finding and Morrison et al. 2007's off-grid solution, and the delay-window scheme is a novel instance of the same idea at the connectome scale). There is nothing further to take from that literature for *this* codebase — it is done, and done more aggressively than any published simulator (the 1.8 ms integration step *is* the literature's `d_min`, raised from a communication-batching trick to the actual solver step). The reproducibility half is different: it is live, unresolved, and the codebase has already diagnosed the exact mechanism (ATen's FMA-fused vector body vs. non-fused scalar tail) that the HPC-reproducibility literature (ReproBLAS, Intel CNR, the 2024 FPNA survey) describes generically. The single actionable finding from this literature is that the per-neuron LIF sweep has **no cross-lane reduction** — it is pointwise, so none of the classical reproducible-summation machinery (Kahan, 2Sum, ReproBLAS) is needed for it; that machinery *is* needed, if ever, only for `lif_fanout`'s `acc[p] += val[k]` scatter accumulation, which is cheap (0.14% of runtime) and should be left alone. And the "certified silence" bound (§5.2, §2.5 of HANDOFF.md) is validated by sampling 20,000 random states, not by a machine-checked bound on the floating-point evaluation of the closed form — Gappa or FPTaylor can turn that into an actual proof cheaply, because the certify pass is 6.92 ms and not on the hot path.

## Applicable techniques

### 1. Rotter & Diesmann (1999) exact propagator — already adopted, cite it correctly
**Citation:** Rotter, S., Diesmann, M. "Exact digital simulation of time-invariant linear systems with applications to neuronal modeling." *Biol. Cybern.* 81, 381–402 (1999). https://link.springer.com/article/10.1007/s004220050570 · DOI 10.1007/s004220050570
**Core idea:** for any time-invariant linear ODE (matrix `A` constant), the matrix exponential `exp(Ah)` propagates the exact state over an arbitrary step `h`, including a train of `δ`-pulses folded in via the pulse-response formula. No discretization error at all — the "grid" only samples an otherwise-exact trajectory.
**Key equation:** `x(t+h) = exp(Ah) x(t) + ∫₀ʰ exp(A(h-s)) B u(t+s) ds`, specialised for the 2×2 block `(v,g)` per neuron to the polynomial form already in ROADMAP.md §5.1: `u(h) = x·u0 + (g0/3)(x - x⁴)`, `g(h) = x⁴·g0`.
**Speedup:** none — same FLOP count as Euler (3 mul + 2 add vs 2 mul + 3 add, per HANDOFF.md §4).
**Fidelity verdict:** exact (not bounded-error) for the sub-threshold flow; this is the correction to the reference's own inexactness, not a performance optimisation, and it is already implemented (commit `0fa5b47`).

### 2. Morrison, Straube, Plesser & Diesmann (2007) + Hanuschkin et al. (2010) — off-grid spike timing, already the delay-window scheme
**Citation:** Morrison, A., Straube, S., Plesser, H.E., Diesmann, M. "Exact subthreshold integration with continuous spike times in discrete-time neural network simulations." *Neural Comput.* 19(1), 47–79 (2007). DOI 10.1162/neco.2007.19.1.47.
Hanuschkin, A., Kunkel, S., Helias, M., Morrison, A., Diesmann, M. "A general and efficient method for incorporating precise spike times in globally time-driven simulations." *Front. Neuroinform.* 4:113 (2010). https://www.frontiersin.org/journals/neuroinformatics/articles/10.3389/fninf.2010.00113/full
**Core idea:** combine exact sub-threshold integration (item 1) with an analytic threshold-crossing test so the spike time is not snapped to the grid; NEST's `iaf_psc_exp_ps` implements this generically for any neuron with a threshold condition, independent of the specific sub-threshold dynamics.
**Key equation / algorithm:** advance the state exactly to the grid point, then, only if `v > θ` at the checkpoint, solve for the crossing time analytically on the interval and re-integrate from there — the crossing time is found from the same closed form as item 1, not from bisection on the grid.
**Cost:** the paper reports the time-driven precise method has *lower* administrative overhead than the older event queues it replaced, and identical scalability to the plain grid solver — i.e., the exactness is close to free once you already pay for exact integration.
**Quantified accuracy cost of dt = 0.1 ms grid detection (measured on this codebase, HANDOFF.md §4):** vs. a dt = 0.002 ms reference, grid detection at dt = 0.1 ms lost ~10% of spikes (42 vs 47) and gained +1 spurious spike in a 400-neuron deterministic test (159 vs 158 truth) — consistent with Hansel et al. 1998's mechanism below. **The accepted fix, exactly as this codebase already implements it, is analytic crossing detection, not a finer grid** (finer grids only shrink, never eliminate, the loss, and cost proportionally more compute).
**Fidelity verdict:** exact (bit-for-bit against the true continuous-time crossing, to floating-point precision) — this is what the codebase's quartic solver + certified-silence pair already deliver (`exact_spike_time.py`, `window_step.py`), independently converging on the literature's answer.

### 3. Hansel, Mato, Meunier & Neltner (1998) — why dt = 0.1 ms costs what it costs
**Citation:** Hansel, D., Mato, G., Meunier, C., Neltner, L. "On numerical simulations of integrate-and-fire neural networks." *Neural Comput.* 10(2), 467–483 (1998). DOI 10.1162/089976698300017845. PMID 9472491.
**Core idea:** naive Euler/RK2 on a fixed grid systematically desynchronises firing because the reset is applied only at grid points; the true crossing (which happens strictly *between* grid points on average `h/2` early) is rounded forward to the next grid tick, delaying every reset by up to one full `dt` and corrupting synchrony statistics in recurrent networks even when the per-step voltage error is tiny. They propose linear interpolation of the crossing time as a cheap partial fix (a precursor of item 2).
**Key equation:** for a linear interpolant between the sub-threshold and post-threshold grid samples, the estimated crossing time is `t* = t_n + h·(θ - v_n)/(v_{n+1} - v_n)`, materially closer to truth than snapping to `t_{n+1}`.
**Fidelity verdict:** bounded-error (the interpolation itself is not exact for a nonlinear or even affine sub-threshold flow) — this codebase's item-2 machinery supersedes it by using the true affine flow instead of a linear interpolant, so Hansel et al. is cited here only as the diagnosis, not as a technique to adopt; adopting it *instead of* the exact quartic solver would be a regression.
**Fidelity verdict:** superseded — do not implement, the current approach is strictly better.

### 4. Krishnan, Porta Mana, Helias, Diesmann & Di Napoli (2018) — "perfect detection", a stronger version of the codebase's own certified-silence idea
**Citation:** Krishnan, J., Porta Mana, P., Helias, M., Diesmann, M., Di Napoli, E. "Perfect detection of spikes in the linear sub-threshold dynamics of point neurons." *Front. Neuroinform.* 11:75 (2018). https://www.frontiersin.org/journals/neuroinformatics/articles/10.3389/fninf.2017.00075/full
**Core idea:** the standard end-of-interval test `v(t₀+h) ≥ θ` is *sufficient but not necessary* — it misses states that cross threshold and return sub-threshold within the same interval (a double crossing). They derive the exact spike/no-spike region in state space by propagating the threshold hyperplane *backward* in time; for affine dynamics the no-spike region is bounded by two linear inequalities (the backpropagated threshold at `t=0` and `t=h`) plus one nonlinear "envelope" inequality from the critical points of the flow.
**Key equation:** no-spike region ⇔ `V < θ ∧ V < f_h(I) ∧ V < b(I)`, where `b` is the closed-form envelope of the backpropagated family of threshold surfaces (their eq. 25).
**Cost:** reported 20–30% slower than the standard grid test — cheap relative to this codebase's own quartic solver (38x per §2.9 of HANDOFF.md), because it only needs to be evaluated at the certify step, not per grid step.
**Relevance:** this is a *published, closed-form, floating-point (not sampled) proof* that a given interval contains no crossing — precisely the kind of certificate HANDOFF.md's §2.5 currently only supports empirically (20,000/20,000 sampled agreement). Worth reading before hardening the certify predicate (item 4 below), because it may already contain the exact inequality this codebase would otherwise have to re-derive.
**Fidelity verdict:** exact (lossless, by construction — the paper's own name for the method).

### 5. Reproducibility diagnosis — FMA fusion divergence between vectorized and scalar code, generically
**Citation:** (survey) "Impacts of floating-point non-associativity on reproducibility for HPC and deep learning applications," arXiv:2408.05148 (2024). https://arxiv.org/pdf/2408.05148
**Core idea:** compilers/libraries routinely contract `a*b+c` into a single fused-multiply-add in the vectorized main body (one rounding) while a scalar remainder/tail loop — compiled from different code, or hitting a different intrinsics path — computes the same expression as two separate roundings; the resulting bit pattern is then a function of vector width and therefore of how many elements land in the tail, which is itself a function of thread count when work is chunked per-thread before vectorizing each chunk.
**Relevance — this is exactly what `lif_kernel.c`'s own comments (lines 19–26, 131–143, 202–206, 266–276) already diagnosed independently, empirically, on this machine:** `v.add_(t, alpha=)` is `fmaf` (1 rounding) in ATen's vectorized body, but the last `(chunk_len mod 16)` neurons of *each per-thread chunk* fall through to a non-fused 2-rounding scalar path — verified by the kernel authors to diverge at 1 ULP if reproduced wrongly (comment: "forcing the separate two-rounding form here diverges from the reference at step 33, versus step 514 with the FMA"). The paper's contribution here is not new information but **external validation that this is a known, general phenomenon** (not an artifact of this one profiling session) — useful to cite when writing this up for review, since "we found a 1-ULP divergence in ATen" is a much stronger claim with a citation showing it is a recognized class of bug, not a fluke.
**Fidelity verdict:** the current mitigation (hardcode the reference's own chunk boundaries as data, reproduce both roundings explicitly per position) is bit-identical **to that one PyTorch build/thread-count's golden run** — see "Ruled out" below for why this is a narrower claim than "reproducible."

### 6. ReproBLAS / Demmel & Nguyen — the CS-formal definition of "reproducible," and why it is the wrong target here
**Citation:** Demmel, J., Nguyen, H.D. "Fast Reproducible Floating-Point Summation." *21st IEEE Symposium on Computer Arithmetic* (2013). https://www.researchgate.net/publication/261025034_Fast_Reproducible_Floating-Point_Summation · Ahrens, P., Demmel, J., Nguyen, H.D. "Algorithms for Efficient Reproducible Floating Point Summation." *ACM TOMS* 46(3), 2020. https://dl.acm.org/doi/fullHtml/10.1145/3389360 · project page http://bebop.cs.berkeley.edu/reproblas/
**Core idea:** define "reproducible" as *bitwise identical regardless of thread count, data partitioning, or reduction order* — not identical to any particular reference implementation. Achieved by rounding every addend to a common fixed-point grid derived from a computed bound on the sum, so the rounded values can be added in *any* order with an exactly representable (error-free) partial sum, then reconstructed; a 6-word accumulator needs ~7n additions per n-element sum.
**Key algorithm:** compute `M = max|xᵢ|`; choose a binade `2^e ≤ M`; round each `xᵢ` to a multiple of `2^(e-52+K)` (double precision, K-bit accumulator slack) so summation of the rounded values is exact and therefore order-independent; reconstruct.
**Expected cost, worked for this kernel:** the per-neuron sweep has **no summation over neurons at all** — it's `N` independent 2-state updates, so ReproBLAS-style accumulation is not applicable there. It *is* the right tool for `lif_fanout`'s `acc[p] += val[k]`, which sums multiple synaptic contributions landing on the same postsynaptic neuron `p` — but that reduction touches ~7,174 ops/step (§2.7 of HANDOFF.md), 0.14% of runtime; ReproBLAS's own measured overhead is **~8x slower than a plain sum on one core** (per Intel CNR benchmarks below, and ReproBLAS's own SC13 slides), so ReproBLAS-ing 0.14% of the runtime at 8x cost adds ~1% overhead total — affordable, but only worth doing if the *goal* changes from "bit-identical to this ATen build" to "reproducible regardless of our own thread count," which is a different, currently unneeded property (see next item).
**Fidelity verdict:** exact, and additionally thread-count/order-independent — a strictly stronger and more expensive property than what this codebase currently needs.

### 7. Intel Conditional Numerical Reproducibility (CNR) — same tradeoff, industrial version
**Citation:** Intel oneMKL developer guide, "Obtaining Numerically Reproducible Results" / "Reproducibility Conditions." https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-windows/2024-1/reproducibility-conditions.html
**Core idea:** oneMKL guarantees bit-reproducibility *conditional on* a fixed thread count and a single executable/run — the same conditional-reproducibility posture this codebase already has (its "bit-identical" claim is likewise conditional, on ATen's thread count at golden-reference-capture time). "Strict CNR" mode lifts the thread-count condition at a measured **~2x slowdown for large-array summation**.
**Relevance:** names and legitimizes the exact tier this codebase is already operating at ("conditional," not unconditional, reproducibility) — useful vocabulary for the write-up (`verify_pytorch_perf.py`'s gate should be documented as "conditionally reproducible: exact match to a pinned PyTorch build + thread count," not "reproducible," to avoid an unqualified claim that later breaks when torch is upgraded).
**Fidelity verdict:** n/a — this is a naming/scoping reference, not a technique to implement.

### 8. Kahan / Two-Sum / Ogita–Rump–Oishi error-free transformations
**Citation:** Kahan, W. "Further remarks on reducing truncation errors." *Commun. ACM* 8(1), 40 (1965). · Ogita, T., Rump, S.M., Oishi, S. "Accurate Sum and Dot Product." *SIAM J. Sci. Comput.* 26(6), 1955–1988 (2005). https://www.tuhh.de/ti3/paper/rump/OgRuOi05.pdf · Muller, J.-M. et al. *Handbook of Floating-Point Arithmetic*, 2nd ed. (2018), ch. on error-free transformations, for the canonical Knuth/Møller `2Sum` algorithm.
**Core idea:** `2Sum(a,b)` computes both `fl(a+b)` and its exact rounding error `e` (`a+b == fl(a+b)+e` exactly, in real arithmetic) using 6 FLOPs and no extended precision; chaining `2Sum` (Ogita–Rump–Oishi "distillation") gives a sum accurate to ~2x working precision at ~4n FLOPs, independent of summation order's *accuracy* (though still order-dependent in its *bit pattern* unless combined with ReproBLAS-style rounding).
**Key equation:** `s = fl(a+b); b' = s - a; a' = s - b'; e = (a - a') + (b - b')`.
**Relevance:** this is the mechanism *underneath* ReproBLAS (item 6); it is the right primitive if `lif_fanout`'s scatter-accumulate is ever the thing being hardened, and it is also the primitive one would reach for if cross-validating against Brian2 (Next Steps item 7 in HANDOFF.md) with an accumulation order that owes nothing to either simulator's internal chunking — i.e., a neutral, maximally-accurate reference sum to diagnose *whose* rounding is closer to truth, rather than which one matches which.
**Fidelity verdict:** exact-to-within-K-ULPs, a genuine accuracy improvement over plain summation, but solves an accuracy problem, not this codebase's current bit-identity problem.

### 9. Gappa / FPTaylor — machine-checked floating-point error bounds, upgrade path for the certify predicate
**Citation:** de Dinechin, F., Lauter, C., Melquiond, G. "Certifying the floating-point implementation of an elementary function using Gappa." *IEEE Trans. Computers* 60(2), 242–253 (2011); Gappa tool paper: Daumas, M., Melquiond, G. "Certification of bounds on expressions involving rounded operators," arXiv:cs/0701186. https://arxiv.org/pdf/cs/0701186 · Solovyev, A., Jacobsen, C., Rakamarić, Z., Gopalakrishnan, G. "Rigorous Estimation of Floating-Point Round-off Errors with Symbolic Taylor Expansions." *ACM TOPLAS* 41(1) (2018), tool: FPTaylor, https://github.com/soarlab/FPTaylor
**Core idea:** Gappa combines interval arithmetic with forward error analysis to derive, and machine-check (in Coq/HOL Light), a rigorous enclosure for the rounding error of an arbitrary arithmetic expression written in ordinary C-like syntax. FPTaylor instead builds a symbolic first-order Taylor form of the rounding error and globally optimizes it over the input domain, typically producing tighter bounds than pure interval methods, with per-instance certificates checkable in HOL Light.
**Key idea for this codebase:** feed the `KAPPA_WINDOW_MAX` closed form (HANDOFF.md §5.2) and the quartic-solver bracketing test (§5.3) to either tool over the actual reachable input ranges (`v0 ∈ [v_reset, v_th)`, `g0 ∈ [0, g_max]` bounded by max synaptic weight × max fan-in) to obtain a machine-checked bound `sup_h u(h) ≤ analytic_bound + K·ε_fp32` for an explicit, provably-correct `K` — replacing "0/20,000 false-silence certifications observed" with "0/2³² possible, proved."
**Expected cost:** this is a one-time offline analysis (minutes, not a runtime cost) — the certify pass at 6.92 ms/window is unaffected; only the *constant* `KAPPA_WINDOW_MAX` gets a slightly larger, now-provably-safe margin.
**Fidelity verdict:** turns an empirically-validated bound into a machine-checked exact bound — directly satisfies the task's "no information sacrificed" / "provably exact or rigorous error bound with a test" requirement better than sampling does.

## Ruled out from this field, and why

| Technique | Why not, specifically |
|---|---|
| **ReproBLAS / Intel strict-CNR applied to the dense sweep** | The dense sweep has zero cross-neuron reduction — `v[i]`, `g[i]` depend only on neuron `i`'s own prior state (see `lif_kernel.c` lines 74-86: every line is per-`i`). There is nothing to make "order-independent"; the entire premise of ReproBLAS (a reduction whose order varies) does not exist in this loop. Applying it here would add the measured ~2-8x overhead for a problem the kernel does not have. |
| **Reproducing ATen's chunk-seam bit-identity as a long-term compatibility target** | This is a *conditional* reproducibility claim (Intel CNR's own term) — conditional on the exact PyTorch build and the specific thread count active when the golden reference was captured. `lif_kernel.c`'s own comment already says this plainly ("the reference's bit pattern is a function of PyTorch's thread count"). It is the correct target for validating *this specific* kernel against *this specific* golden run, but it is not a durable specification: if torch is upgraded, or the reference regenerated on a different core count, the `chunks[]` data must be recaptured. Recommend documenting this explicitly as a versioned artifact (pin the torch version + thread count used to produce the current golden spike train) rather than as an invariant of the algorithm. |
| **Hansel et al. 1998 linear-interpolation spike timing** | Superseded in this codebase by the exact quartic/affine solver (item 3 above); adopting the 1998 heuristic would be a regression from exact to bounded-error for no benefit — noted only because it explains the historical *size* of the dt = 0.1 ms grid-detection error the codebase already measured (§4 of HANDOFF.md). |
| **Full interval-arithmetic library (e.g., a C++ port of INTLAB/Boost.Interval) for every step of the hot dense sweep** | The certify/predict pass (§2.6, 5.27+6.92 ms/window) is cheap and off the hot 0.219 ms/step dense-sweep path; the dense sweep itself has a fp32 floor of ~200ε ≈ 2.4e-5 mV against a 7 mV threshold (ROADMAP §5.1) — already two orders of magnitude below anything interval bookkeeping would meaningfully tighten, at the cost of 2-10x overhead per operation. The value is entirely in the *certify* predicate (a few hundred evaluations of a short closed form, not per-neuron-per-step), where Gappa/FPTaylor (item 9) is the right-sized tool, not general runtime interval arithmetic. |
| **SparseProp-style rescale for reproducibility purposes** | Not reproducibility-relevant, and already ruled out on other grounds in ROADMAP.md (denormals, O(N)→O(N) not O(log N) here) — restating only to note this literature pass found no new reason to revisit it. |
| **Compensated (Kahan) summation inside the dense sweep loop itself** | There is no summation inside the sweep to compensate — see the ReproBLAS row above. Would add 3-4x the operations (Kahan needs ~4 FLOPs per addition vs. 1) to a loop that has no accumulation error to fix. |

## Concrete next actions for this codebase

1. **Thread `lif_step`'s existing chunk loop (`flyloop/native/lif_kernel.c` lines 278–280) across the 4 physical cores with `std::thread`/OpenMP, dispatching each already-recorded `chunks[c]..chunks[c+1]` range to a worker.** This is provably bit-identical to the current single-threaded output for any number of OS threads used to execute it, because (a) the bit-identity target is the *pinned* `chunks[]` array — data captured once from the golden ATen run — not derived from however many threads actually execute `lif_step`, and (b) each `sweep()` call only reads/writes its own disjoint `[lo,hi)` slice of `v`, `g`, `refrac`, `sp_scratch` with no shared accumulator, so concurrent execution changes no floating-point operation's order. **Arithmetic:** the dense sweep touches roughly 7 arrays of length N=138,639 fp32 (v,g,refrac read+write, refrac_steps read, sp_in/out) ≈ 3.9 MB/step; at the current 0.219 ms/step that's only ~17.7 GB/s of the machine's ~68 GB/s LPDDR4x ceiling — under 4x headroom is unused, comfortably above the 2.19x speedup needed to reach 0.1 ms/step. This is the single highest-confidence, lowest-risk item in the entire roadmap because reproducibility is *not* an obstacle here, it's already solved by construction. Measure actual scaling (bandwidth contention across 4 cores rarely gives the full theoretical factor) — but the ceiling math says there's room even at 50-60% efficiency.
2. **Leave `lif_fanout`'s `acc[p] += val[k]` scatter-accumulation single-threaded and in its current spike-ascending / CSC order.** It is the one place in the kernel with genuine cross-source reduction, it is 0.14% of runtime (§2.1, §2.7 of HANDOFF.md), and parallelizing it would require either ReproBLAS-style rounding (item 6, ~8x local overhead — affordable at this scale but adds real code) or accept a different, order-independent bit pattern that breaks bit-identity to ATen's `scatter_add_`. No action needed unless a future workload makes this the bottleneck (it structurally can't, per the 728:1 ratio in ROADMAP.md).
3. **Add one paragraph to `HANDOFF.md` naming the "conditional reproducibility" scope explicitly** (citing Intel's own CNR terminology, item 7): state that `verify_pytorch_perf.py`'s bit-identical gate is conditioned on a pinned PyTorch build + thread count used to capture the current golden spike train, and record that build/thread-count as a versioned fact next to the golden-data files — so a future torch upgrade produces a clear, expected `chunks[]`-regeneration step rather than a mysterious bit-identity failure.
4. **Harden the certify bound (`code/exact_spike_time.py` / `window_step.py`'s `KAPPA_WINDOW_MAX` and the quartic bracketing test) with Gappa or FPTaylor (item 9)**, run offline against the actual reachable `(v0,g0)` domain, to convert the current 20,000-sample empirical validation (HANDOFF.md §2.5) into a machine-checked bound with an explicit `K·ε_fp32` margin. This is a same-week, no-runtime-cost change (the tools run once, offline, over the closed-form expressions already in the code) and directly strengthens the "0 false-silence certifications" claim from "observed on a sample" to "proved for the domain." Read Krishnan et al. 2018 (item 4) first — its backward-propagated envelope may already be the tighter, closed-form version of the bound this codebase derived independently.
5. **When the accuracy-validation gate against Brian2 is finally run (HANDOFF.md §10 Next Steps item 7), do not compare via either simulator's own internal accumulation order.** Use a neutral Ogita–Rump–Oishi / 2Sum-based reference sum (item 8) for any aggregate statistic used in the comparison (e.g., total spike count, population rate) so that disagreements are attributable to genuine dynamics differences, not to whichever simulator's rounding happens to run closer to a plain left-to-right sum.
